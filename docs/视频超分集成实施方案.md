## 一、架构结论

**将“视频超分”集成到 MediaGrab 左侧菜单，内部采用独立超分模块和按需启动的本地处理进程，暂不新建独立 App。**

MediaGrab 已经具备桌面外壳、媒体下载、任务服务及媒体工具路径管理。用户可以形成“下载视频 → 选择本地或已下载视频 → 超分 → 查看成片”的连贯流程，无需维护第二套应用设置、任务生命周期及安装更新链路。

“界面集成”不等于“引擎耦合”：超分任务、模型与处理管线应独立，未来有专业修复产品需求时可以再拆出应用。现阶段不引入新的顶层项目，也不在桌宠项目中增加超分界面。

## 三、界面与首版范围

### 3.1 左侧菜单

保留现有下载工作区，新增独立的“媒体工具”分组：

```text
工作区
  新建任务
  下载队列
  历史记录

媒体工具
  视频超分

设置
```

超分页面应拆为独立组件，沿用现有视觉风格；不要继续向 `App.tsx` 堆叠完整处理页面，也不要改动现有下载列表语义。

页面至少包括：

1. 通过原生对话框选择本地视频，显示文件名、尺寸、帧率、时长及格式探测结果。
2. 明确标注“动漫 2× 超分”；1080p 的示例输出是 3840×2160，不把任意输入的 2× 输出都叫作 4K。
3. 输出目录及输出文件名；默认生成新文件，不覆盖源视频或已有成片。
4. 明确的开始、取消、阶段进度、已处理帧数及错误信息。
5. 成功后可打开成片或在 Finder 中显示；不能把未校验的中间文件显示为成功结果。
6. 引擎、模型或平台不可用时给出原因，不显示假进度或假成功。

首版先完成本地文件入口。下载历史中的“发送到超分”可作为闭环后的第二步，不作为第一阶段前置条件。

### 3.2 支持边界

- 首要验证平台：macOS Apple Silicon。未验证的平台显示能力限制，不宣称全平台支持。
- 首要样本：SDR、恒定帧率、1920×1080、H.264 / MP4，单路 AAC 音频或无音频。
- 首版模型：`realesr-animevideov3-x2`，固定 2×。普通实拍画面适用性未在本项目验证，不宣传为通用画质修复。
- 不做补帧；保持受支持输入的帧率、帧序与时间线，不将所有输入强行变成原样本的 24 fps。
- 对可直接封装进目标 MP4 的 AAC 音轨优先复制；无音轨正常处理。其它音频策略必须明确，不能静默删音轨。
- HDR、可变帧率、旋转元数据、多音轨、字幕及其它暂未适配情况，探测后明确拒绝或提示限制；不能丢弃信息后仍宣称无损保留。
- 对尺寸、像素数、时长等设置明确安全上限；非标准尺寸如果暂不支持，在开始前报错，不留给编码尾声才失败。
- 完全本地处理，不上传视频，不调用付费 API，不自动处理新下载的视频。

## 四、模块划分

建议在现有 Monorepo 内按下面边界实施，具体文件名可根据当前约定调整，不强行照抄新目录骨架。

### 4.1 前端超分视图

负责文件选择、能力展示、创建任务、状态订阅、取消及展示输出。前端不直接拼接 shell 命令，不自行猜测工具是否可用。

### 4.2 独立超分任务服务

在服务端新增独立超分服务及共享契约，不复用下载任务中 `bvid`、`cid`、`qn`、下载字节速度等字段表达超分。

建议任务记录包括：任务 ID、经授权的输入引用、输出位置、模型及参数、输入探测摘要、状态与当前阶段、完成帧数、总帧数、时间戳、错误代码及已验证结果。

- 状态可分为排队、运行、成功、失败、取消、中断；阶段另行表示探测、解码、超分、编码、校验。
- 小批次处理时阶段会重复切换，不能把单次线性阶段百分比误当全片进度。
- 先做单超分任务并发；下载并发与超分并发分开，不让多个 GPU 推理作业同时启动。
- 复用或扩展现有事件推送及持久化基础，采用独立消息判别值，保持下载协议兼容。
- 重启后能识别遗留运行态并标为中断；首版不必支持断点续算，不能伪装成可以无损续跑。
- 退出时清理本任务子进程，不允许留下无主推理进程；不要扫描并终止系统中其它同名程序。

### 4.3 本地处理引擎

建议由现有 Node 服务负责调度 FFprobe、FFmpeg、Real-ESRGAN 子进程。沿用已经验证过的算法和有界处理思路，但不要求最终用户另装 Python、Pillow 或开发环境。

若必须增加单独 worker，需解释收益、分发方式及生命周期；不复制整个桌宠项目、虚拟环境或硬编码本机路径进入产品。

### 4.4 工具及模型管理

扩展现有工具解析与资源准备流程：

- 分别管理 FFmpeg、FFprobe、Real-ESRGAN 可执行程序和模型目录；不能假设当前 FFmpeg 构建已经附带 FFprobe。
- 校验目标架构、版本、模型组合及 SHA-256；依赖缺失时返回结构化错误。
- 明确选择随包附带或显式安装依赖；不得在启动应用时静默下载模型或升级引擎。
- 本机开发可以显式指定现有工具路径；发行包不能依赖另一个项目的 `.local/` 绝对路径。
- 引入第三方工具和模型前核对来源、许可与再分发条件，保留许可证及第三方声明，不能由本项目 MIT 推断其它资源都可分发。
- macOS 打包后验证嵌套可执行程序签名与实际可运行性；开发机 PATH 下可运行不等于安装包可运行。

## 五、处理流程与资源边界

```text
选择文件 → 探测并检查支持范围 → 创建独立任务目录
        → 有界解码 → 分批/分块超分 → 编码临时视频
        → 合成兼容音轨 → 校验候选成片 → 提交新输出 → 展示结果
```

1. 使用顺序解码、有背压的管道或有界小批次；不能一次性展开整条视频的 PNG，也不把全片帧载入内存。
2. 已验证的参考设置为 tile 256、线程 `1:1:1`、每批最多 12 帧；这些只是起点，不是所有输入的最优设置或内存保证。可下调批次数量，但不得声称减少批次必然同比减少 GPU 模型工作集。
3. 每批完成后及时回收本批帧；应计入输出文件持续增长、临时视频、输入/输出帧和合成占用，不能照抄旧脚本的 512 MiB 空间阈值作为通用保证。
4. 如果复用分段编码与拼接，要处理末批不足一批、时间基、关键参数一致性及 B 帧重排序；也可采用持续编码管线，但必须用测试证明时间线正确。
5. 进度依据实际完成帧和全片规模；不能直接把模型的单帧 tile 进度当作整条视频进度。总帧数未知时显示不确定进度，不伪造 ETA。
6. 先生成任务专属候选文件；尺寸、帧数、帧率、时间戳、时长、音轨及解码验证完成后才提交最终输出。
7. 提交采用目标目录内临时文件及适当的无覆盖提交机制，处理重名与竞争；取消/失败不替换原片、不覆盖已有文件。
8. 失败时保留必要诊断信息；是否保留已完成候选片应有明确规则，不能将其标为成功。清理仅作用于本任务创建且已确认归属的临时文件。
9. 模型只在任务处理中加载，结束后对应推理进程退出；空闲时应用自身仍有常规内存开销，不承诺整个应用零占用。

### 内存实测注意

不能把旧项目报告中的单个超分进程 RSS 当作 MediaGrab 整个应用的峰值，也不能在未复核输入尺寸前沿用“1080p → 4K 约 915 MB”的说法。旧测量的输入来源/尺寸口径需要复核；集成验收必须重新使用明确的原始 1080p 文件测试，先探测并记录输入/输出尺寸。

新测试应分别报告应用空闲内存、处理期间宿主/核心/推理/编解码进程的内存观察、平台/GPU 信息、tile、批次和耗时。macOS 统一内存及共享页让各进程 RSS 简单相加也不等于精确系统总占用；没有可靠总量测量时如实说明，不给未经测量的固定内存承诺。

## 六、本地文件与进程安全

新增本地媒体处理接口意味着后台可能访问更多文件，不能只因为监听 loopback 就默认安全：

- 延续现有核心身份校验及访问控制，检查新增路由、WebSocket、Origin/CORS 边界，不泄露核心令牌。
- 原生文件选择应产生受限的选择结果或文件授权记录；不能向任意网页开放“传入任意路径即可读取/执行”的接口。
- 使用 `spawn` / `execFile` 的参数数组，不使用 shell 字符串拼接；测试空格、中文、引号、前导连字符与特殊字符路径。
- 校验普通文件、规范路径、读写权限、符号链接及输入输出不得指向同一对象；保留用户原文件。
- 输入媒体路径、输出路径不得借由 FFmpeg 参数或媒体引用意外触发网络读取；需要约束处理子进程允许的协议及附带文件访问。
- 任务目录隔离，不清理其它会话、下载目录或全局临时目录；取消只能作用于自己创建的进程及文件。
- 错误信息和日志不写认证信息，不记录视频内容，不默认复制用户私有媒体到仓库。
